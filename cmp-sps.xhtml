Scope

This document defines the rules, procedures and guidelines applied to the development of a software project. It covers:

  • configuration management: how artifacts and work products are identified, versioned and baselined;
  • the software product specification: the targets, data packages and runtime identification that each delivered product shall provide;
  • the implementation rules and plan: build requirements, language requirements, and naming and documentation conventions for each supported language.

This document is a template. Before it is placed in a repository, each item of the form {{A|B}} shall be replaced by the alternative that applies to the project, and each item of the form {{name}} shall be replaced by the project value. This paragraph shall then be removed.

Conventions, terms and references

Conventions

The key words “shall”, “shall not”, “should”, “should not” and “may” in this document are to be interpreted as described in [ISO-DIR-2]:

shall
An absolute requirement. A deviation makes the work non-conforming.
shall not
An absolute prohibition.
should
A recommendation. Deviation is permitted where the reasons are understood and the consequences accepted, but the deviation should be recorded.
should not
A recommendation against.
may
A permission. The choice is left to the implementer, and neither option is preferred.

Configuration management

Configuration identification

The items (work products, artifacts) placed under configuration management (tracked, stored and versioned) as well as baselining through tagging are identified with the rules defined in the following sections.

Generic definitions

Throughout this document, the following definitions are reused:

<module_name>
The name of one module of the repository, equal to its artifactId in Maven builds. In a repository with a single module, <module_name> is equal to <project_name>.
<project_name>
The project name, used as a mnemonic for the project, such as the repository or product, throughout its lifecycle.
<project_version>

The actual project version, following the semantic versioning scheme [SEMVER2].

The software version is composed of three parts. An increment of the MAJOR version indicates non-interchangeable or incompatible breaking changes. A MINOR version increment indicates additional functionality while keeping backward compatibility, while a PATCH version increment indicates a bug or problem fix.

A snapshot label, -SNAPSHOT, is appended to the project version when the software is not yet released and is still in development. This is equal to the Maven version element.

All the modules of a repository shall share one <project_version>. A new version shall be assigned to all the modules together, including modules that have not changed.

Baseline identification

When a baseline needs to be identified, the baseline identifier shall follow the rule below:

baseline_identifier ::= <project_version>

Runtime identification

Runtime identification of the software shall have the following format in EBNF syntax:

agent_name ::= <vendor> " " <module_name> " " <project_version> [ "(" <token> { ";" <token> } ")" ]
vendor     ::= "OptimaSC"
token      ::= token_char { token_char }
token_char ::= "A".."Z" | "a".."z" | "0".."9" | "-" | "." | "_"

The terms are defined above, except for the following:

  • <token> can be used to identify an operating system, build variant, plug-in, or more detailed version information.

The above form is equivalent to the XMP AgentName [ISO-16684-1].

Data package naming conventions

Each module shall produce its own data packages, named with its <module_name>. Data packages that combine several modules, such as a complete source or binary distribution, shall be named with the <project_name>.

The generic data package naming (main artifacts) conventions are as follows, in EBNF syntax:

data_package_name ::= ( <module_name> | <project_name> ) "-" <project_version> [ "-" <classifier> ] "." <suffix>
classifier        ::= "bin" | "src" | "autodoc" | "docs" | "debug" | <platform_name>
suffix            ::= "zip" | "jar" | "asc" | "tar.gz"

Each new term is defined below:

<platform_name>
The name of the target platform when the target is native compiled.
<classifier>
The actual package qualifier. If the package contains application executable software, this qualifier provides the target platform name it was built for. For other packages, the following are possible:
bin
The full package, including binaries.
src
The software source code.
autodoc
The documentation generated from the software source code.
docs
The user documentation.
debug
The debug version of the software.
<suffix>
The data package suffix, depending on the artifact type.

Items placed under configuration control

Items under configuration management are held by one of two mechanisms:

  • Version control — items authored by the project, stored in the repository defined in Branching and merging policy. This comprises source code, build files, configuration files, test sources and test data, project documentation, and any resource required to reproduce a build from a clean checkout. Generated files shall not be committed.
  • Artifact repository — items produced by a build, deployed to a snapshot or production repository as defined in Establishing a configuration baseline, and identified by the data package naming conventions. Deployed artifacts are immutable; a correction requires a new version.

Branching and merging policy

All items under configuration management are stored in a single version control repository per project. The default branch is the branch configured as such in the repository (main for Git) and shall remain buildable at all times. No long-lived feature, release or maintenance branches are used.

Changes authored directly by a project developer may be committed to the default branch. Changes authored wholly or partly by an automated agent or by an external contributor shall be committed to a short-lived branch and merged into the default branch only through a pull request, which shall be reviewed and approved by a project developer before merge. The approving developer may be the same developer who initiated or prompted the change. Merges shall be performed as a squash merge, producing a single commit on the default branch. Such branches shall be deleted after merge and shall not be baselined or tagged.

Baselines are recorded as annotated tags on the default branch, following the scheme defined in Establishing a configuration baseline.

Commit messages

Each commit message consists of a summary line of at most 72 characters, written in the imperative mood, optionally followed by a blank line and a detailed description.

Where a change was authored wholly or partly by an automated agent, the commit message shall end with a trailer identifying it:

Agent: <tool_name> <tool_version>

The trailer is placed on its own line, after any blank line separating it from the description.

Dependency policy

This policy applies to dependencies distributed with or linked by the software, including transitive dependencies, and to third-party source code incorporated directly into the repository. Tools executed during the build but not distributed are not subject to it.

  • A production baseline (PBL) shall not contain any dependency whose version carries the -SNAPSHOT label, and the project version at a PBL shall not carry that label. Only released versions shall be used.
  • Permitted licences: works dedicated to the public domain (CC0 1.0, Unlicense); MIT; ISC; BSD 2-Clause and 3-Clause; Zlib; Apache License 1.1; Apache License 2.0; Mozilla Public License 2.0; Eclipse Public License 1.0 and 2.0; Common Public License 1.0.
  • Dependencies under MPL 2.0, EPL or CPL may be used unmodified. Where such a dependency is modified or forked, the modified files remain under their original licence and shall be published accordingly.
  • Dependencies under the GPL, AGPL, LGPL, SSPL, or any licence prohibiting commercial use or derivative works shall not be used. A dependency with no stated licence shall be treated as all rights reserved and shall not be used.
  • Licences requiring acknowledgement in advertising materials, including the BSD 4-Clause Licence, shall not be used.
  • Required copyright notices, and any acknowledgement or NOTICE content required by the Apache License 1.1 or 2.0, shall be reproduced in a THIRD-PARTY-NOTICES file at the root of each distribution archive.

Establishing a configuration baseline

This section lists the different baselines that exist for this project as well as the rules associated with these baselines.

Two types of baseline are available. The Production Baseline (PBL) is used for software to be used in production. It is allocated by the Configuration Control Board (CCB) when the project is ready for release, and consists of the following actions being completed:

  • A version description document is generated and is available.
  • Items under version control used for building the production data packages and/or distribution archives are tagged with a tag name equal to v followed by the <baseline_identifier>, for example v1.2.0.
  • A software label identifying the version is available at runtime.
  • Generated data packages and/or distribution archives are deployed to the production repository.

The developmental baseline is used when non-stable software, which has minimal working functionality, needs to be released for testing or to a wider selected audience. This baseline can be allocated at any time deemed necessary by the Configuration Control Board. It consists of the following:

  • Generated data packages and/or distribution archives are deployed to a snapshot repository.

Status accounting

This section describes the schedule for generating configuration status reports as well as their contents. The current status reports are as follows:

  • Version description document

The version description document is generated before the establishment of a PBL.

Version description document content

A version description document, also called release notes, shall contain the following information, available at each production baseline (PBL) for each module:

  • A brief statement of the purpose of the software and the environments to which this document applies.
  • Prerequisites for usage of the software, such as minimum operating environment requirements or dependency information.
  • The list of all important changes incorporated into the software version since the previous version.
  • Installation or build instructions.
  • Known issues and problems.

The version description document is an artifact available in the deployment repository. The files that carry it for each language are defined in Java version description documents and C version description documents.

Build targets and phases

The following targets (Makefile) or phases (Maven) apply to all projects, whatever their language. Build targets executed from the root of the repository shall apply to all its modules, in dependency order.

Main targets and phases

clean
Clean all files generated by compiling and preparation of the distribution files. Among others it cleans generated resources, documentation, compilation artifacts and data packages. It does not however delete build configuration data used for building.
compile
Compiles and links if necessary the software and generates all related data used directly by the software (such as resources). By default, compilation includes debugging information.
deploy
Copies the final data packages or distribution archives to the remote repository for sharing with others.
install
In the case of a library, installs the package into the local repository, for use as a dependency in other projects locally. Package installation installs everything for the distribution, including documentation, resources and compiled binaries.
package

Create a distribution archive for this software containing the binaries, resources and documentation. The root of the archive is the actual directory name of the software project name, with a potential version name, for example myproject-1.0.0. The package target explicitly depends on all non-source files that are in the distribution, to make sure they are up to date in the distribution, including generated documentation and resources.

This target may also generate data packages in required formats used for deployment in the deploy target.

test
Test the compiled source code through a unit testing framework. Testing does not require the software to be deployed or installed beforehand.
uninstall
In the case of a library, delete the previously installed files from the local repository, including configuration data. This target does not modify the directories where compilation is done, only the directories where files are installed.

Other targets and phases

initialize
Used to initialize build state, e.g. set properties or create directories.
generate-sources
Generate any source code or resources for inclusion in compilation. For Makefiles, to be compliant with the POSIX standard, the target name is generate_sources.
autodoc
Generate auto-generated documentation from source code.
distclean
Performs clean and also removes the distribution archives (Makefile builds only).

Java projects

Software requirements

The following requirements are needed to build and package the software:

  • Java Development Kit 1.6 or later. The build requires a JDK that still supports the Java 6 source and target levels; JDK 8 or JDK 11 is recommended. Later JDKs removed support for these levels and cannot be used.
  • Maven version 3.2.5 or later.
  • JUnit 3 testing framework.
  • GnuPG, used for deployment to Maven Central:
    • public/private key pairs associated with the deployment.

Java compilation follows the Maven POM model version 4.0.0.

Hardware requirements

  • At least 40 MiB of free hard disk space.

Build system configuration

All Java projects automatically generate a standard MANIFEST.MF file, which shall contain at minimum the following information, if specified in the Maven project file:

Implementation-Vendor
${project.organization.name} property
Implementation-Title
${project.name} property
Implementation-Version
${project.version} property
Build_Target
The Java runtime target
Module-Name
${project.artifactId} property

The version shall be defined once, in the parent POM of the repository for multiple-module repositories, and inherited by every module.

The Maven POM files contain the following profiles:

dev
Generates the release executable artifacts for deployment to a local repository with optimizations enabled, if applicable, and limited debugging information (source and line information, -g:source,lines), as well as API documentation in the packaging required for repository deployment. This is the default active profile when building.
release
Generates the release artifacts for deployment to the deployment repository with optimization, signing and limited debugging information, as well as generic source, binary and documentation packages for local web site distribution. The release profile enforces the dependency policy through the requireReleaseDeps and requireReleaseVersion rules of the Maven Enforcer plugin.
compliance
Verifies, by an API signature check, that the runtime library use complies with the target API defined in Source code conventions. Activated automatically in Eclipse; can be activated explicitly on the command line.
debug
Generates the debug executable artifacts with the debug classifier for local repository deployment with full debugging information — source file names, line information and local variable information (-g).

The following properties may be modified to change some of the options:

maven.compiler.source
Sets the source version for compilation. This shall be set to 1.6.
maven.compiler.target
Sets the target version for compilation. This shall be set to 1.6.
gpg.keyname
Sets the key ID used for signing the artifacts.

Build procedure

The following steps should be followed for project building and deployment, from the root of the repository:

  1. Execute mvn install to build and install the dev profile package for day-to-day development.
  2. Execute mvn -P debug install to build and install the debug profile packages.
  3. Execute mvn site to build the documentation associated with the project.
  4. Execute mvn -P release package to generate and sign the standard release artifacts, as well as independently installable release packages.
  5. Execute mvn -P release deploy to generate, sign and deploy the standard release artifacts, as well as independently installable release packages.

Source directory structure

Source code for Java projects follows the Maven directory structure, in each module:

DirectoryContents
src/main/javaProduction source code
src/main/resourcesProduction resources
src/test/javaTest source code
src/test/resourcesTest data
src/changesChange list (changes.xml)

The target directory is generated and shall not be committed.

Source code conventions

  • Source code shall be encoded in UTF-8 with no BOM, and lines shall end with a line-feed character (following the UNIX convention for line endings).
  • The language syntax and class file format target Java 6. The class library API is restricted to that of Java SE 6. Where a project targets a constrained environment, this restriction is narrowed accordingly and stated here. Target environment restriction for this project: {{None|Java CDC Foundation Profile 1.1 API}}.
  • The use of the runtime library shall be verified during the build, through the compliance profile.
  • When using elements that support generics, the generic type is explicitly written. For example, a List of String shall be declared as List<String>.
  • Fields and methods used strictly internally shall be declared protected rather than private, so that derived classes may reuse them. private shall be used only where a subclass overriding or accessing the member could break a documented class invariant, or where a specific target runtime is demonstrated to benefit from non-virtual dispatch.
  • The indentation style shall follow the Allman style. This style puts the block statement start character (brace) associated with a control statement on the next line, indented to the same level as the control statement. Statements within the block are indented to the next level.
  • Each indentation level consists of 2 space characters (ASCII character 32). For example, a 2-level-deep indentation is 4 characters.
  • Each source code line has a maximum width of 80 characters. When a line needs to be split, each subsequent line is indented by 1 level.
  • Public methods shall validate their arguments and throw IllegalArgumentException for values outside the documented range, or NullPointerException for a null argument where null is not accepted. Protected and package-private methods may assume valid arguments where the calling contract is documented.

Naming conventions

Naming shall follow the conventions of [JLS] and Oracle's Code Conventions for the Java Programming Language, as summarized below.

Identifier typeCase / formatRuleExamples
Classes and enumerationsPascalCase Should be nouns that are simple and descriptive. Customer, OrderService, HTTPRequestHandler, URI
InterfacesPascalCase Often nouns or adjectives indicating a capability. Runnable, Serializable
Type parametersSingle upper-case letter A single upper-case letter. T, E, K, V
MethodslowerCamelCase Should be verbs or verb phrases that clearly indicate the action. run(), getBackground(), calculateSum()
Fields, parameters and variableslowerCamelCase Should be short yet meaningful nouns that describe their purpose. i, j and k may be used as temporary integer variable names for counter or index variables in loop constructs. index, i, firstName, width, baseURI
ConstantsUPPER_SNAKE_CASE Written in all capital letters with words separated by underscores. MAX_LENGTH, WIDTH
Packageslowercase Always completely lowercase. Uses a reverse internet domain style for global uniqueness. The default package prefix is com.optimasc. com.optimasc.module

Abbreviations and acronyms shall be written in full upper case in every identifier type that uses PascalCase or lowerCamelCase.

Source code documentation conventions

All code documentation shall follow the standard Javadoc conventions as defined by [JAVADOC], and shall be written in English.

  • Each publicly visible identifier shall be documented with its purpose.
  • Each non-publicly visible method shall be documented with its purpose.
  • Each identifier may be documented with any limitations and constraints on its usage.
  • Each publicly visible package may be documented with additional detail on its usage in a separate package.html file.

Classes and interfaces shall include a summary sentence describing the class's purpose and role within the architecture, followed by a detailed description covering intended usage and relationship to other classes in the framework. Each publicly visible class or interface shall state whether it is thread-safe. Classes shall include @author and @since tags. The @since tag value is based on the project version.

Fields shall include a summary sentence describing the field's purpose and the meaning of its value. Constants shall document their specific value and where they are used.

Methods shall include:

  1. A summary sentence (the first sentence, ending at the first period followed by whitespace) that concisely states what the method does. This sentence appears in Javadoc index pages and must be self-contained.
  2. A detailed description, when warranted, explaining behaviour, preconditions, postconditions and side effects.
  3. An @param tag for every parameter, describing its purpose, valid range, and whether null is accepted. Just before the description of the parameter, a qualifier in brackets states the direction of the parameter: [in] if it is strictly an input parameter, [out] if it is strictly a parameter updated by the method, and [in,out] if its contents are used both as input and output. The direction convention is project-defined rather than standard Javadoc.
  4. An @return tag describing the return value and its meaning, including possible null returns.
  5. An @throws tag for every checked exception, documenting the specific conditions under which it is thrown. Unchecked exceptions (e.g. IllegalArgumentException, NullPointerException) shall be documented with @throws when the method explicitly validates and throws them.
  6. Where a method accepts or returns null, this shall be stated in the corresponding @param or @return tag. Absent such a statement, null is neither accepted nor returned.

Dependency requirements

In addition to the dependency policy:

  • Module external dependencies shall be limited to only what is mandatory.
  • A dependency shall be compatible with the language level and runtime target of the module using it.

Testing requirements

Testing shall be based on JUnit 3.

Test classes shall reside in the same package as the class under test, with a name formed by appending Test to the name of that class. For example, the tests for com.optimasc.entity.Entity are in com.optimasc.entity.EntityTest.

Version description documents

The list of changes shall be src/changes/changes.xml, in the format of the Maven Changes plugin. It shall be published as CHANGES.txt in the release artifacts and as a changes report on the project site.

The remaining information required for the version description shall be placed in a README.md Markdown file at the root of each module.

Source code conventions

  • Source code shall be encoded in UTF-8 with no BOM, and lines shall end with a line-feed character (following the UNIX convention for line endings).
  • Source code shall conform to ISO/IEC 9899:1990 (C90) [ISO-9899-1990], except that where an integer type of a specific range is required, the fixed-width type names defined in <stdint.h> by ISO/IEC 9899:1999 (C99) [ISO-9899-1999] shall be used. If the toolchain does not provide <stdint.h>, the project-supplied compatibility header is used.
  • Source code file names shall be composed of the characters [a-z0-9_] only, shall begin with a letter, and shall be at most 14 characters excluding the suffix. The suffix shall be .c for source files and .h for include files.
  • All variables and procedures that are strictly used internally are made static by default.
  • The indentation style shall follow the Allman style. This style puts the block statement start character (brace) associated with a control statement on the next line, indented to the same level as the control statement. Statements within the block are indented to the next level.
  • Each indentation level consists of 2 space characters (ASCII character 32). For example, a 2-level-deep indentation is 4 characters.
  • Each source code line has a maximum width of 80 characters. When a line needs to be split, each subsequent line is indented by 1 level.
  • Functions and variables use lower_snake_case. Public functions carry a module prefix matching the module name: the functions of stack.c are named stack_*.
  • Types declared with typedef use PascalCase. Struct and union tags use lower_snake_case.
  • Macros and enumeration constants use UPPER_SNAKE_CASE.
  • Identifiers shall not begin with an underscore, and shall not contain a double underscore, as such names are reserved to the implementation.
  • Each include file shall be protected by an include guard. The guard macro name is the file name converted to upper case, with the period replaced by an underscore — for example, stack.h uses STACK_H. The guard consists of #ifndef and #define immediately after the file comment block, and a matching #endif as the last line of the file.

Source code documentation conventions

All code documentation shall follow the standard Doxygen conventions [DOXYGEN], and shall be written in English.

Each source and include file shall begin with a file comment block containing:

  • an @file tag naming the file;
  • a summary sentence describing the file's purpose and role within the architecture, followed by a detailed description where warranted;
  • an @author tag for each author;
  • where the file is adapted from third-party material, a statement identifying the origin and its licence.

Variables, constants and defines shall include a summary sentence describing the item's purpose and the meaning of its value. Constants shall document their specific value and where they are used.

Procedures shall include:

  1. A summary sentence (the first sentence, ending at the first period followed by whitespace) that concisely states what the procedure does.
  2. A detailed description, when warranted, explaining behaviour, preconditions, postconditions and side effects.
  3. An @param tag for every parameter, describing its purpose, valid range, and whether null is accepted. The direction of the parameter shall be stated with [in], [out] or [in,out] as specified in the Doxygen documentation.
  4. An @return tag describing the return value and its meaning, including possible null returns.

Testing requirements

Tests are self-contained C programs, each with a main function, located in tests. No third-party testing framework is used. Checks are expressed using the standard assert macro of <assert.h>.

Test programs shall be compiled without NDEBUG defined, in all configurations, so that assertions are always active.

A test program returns EXIT_SUCCESS when all its assertions pass. A failed assertion terminates the program with a non-zero status and a diagnostic on standard error. A test program that cannot run in the current environment shall exit with status 77, which indicates that the test was skipped. A test program shall produce no other output on success.

One test program shall be provided per module under test, named after that module: the tests for src/stack.c are in tests/stack.c. Test programs are built into build/<target_name>/<config>/tests, so that their intermediate files and executables do not collide with those of the module under test.

The test target shall build and run every test program, report the result (passed, failed or skipped) of each, and fail if any test program exits with a status other than 0 or 77.

Test programs shall conform to the same source code conventions as the software under test, and shall not depend on files outside tests and tests/data.

The test target runs each test program with the project root as the working directory; test data is referenced by the relative path tests/data.

Version description documents

The change log shall be a CHANGES.txt file at the root of the module, maintained manually.

The remaining information required for the version description shall be placed in a README.md Markdown file at the root of each module.
